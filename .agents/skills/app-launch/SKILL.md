# Reusable App Launch

Read the destination's AGENTS.md and applicable ai/ references first. This extension complements the synchronized guidance; it does not change upstream files or grant permission to provision accounts, enable billing, deploy, publish, or start recurring work.

## Scope and configuration

Keep the app name, domain, budget, cloud IDs, owner bootstrap identity, actual routes and connection evidence in project documentation outside this skill and ai/. Preserve the destination's framework, theme, data and narrower access policies. Treat commerce, payments, ads and community features as separate opt-in modules, not consequences of copying guidance.

Record each milestone as source-ready, validated, connected, or deployed, with the actual evidence and remaining blocker. A typed adapter or visible screen is not a connected service. Honor the repository's validation permissions before tests, builds or browser checks.

## Account and dashboard readiness

- Read ai/skills/authentication/authentication.md and the applicable admin references. Define typed account, profile, role, analytics and service-status contracts before provider implementation.
- Leave disconnected services visibly unavailable. Do not accept or persist passwords in a local mock, fabricate sessions, assign Owner to a first sign-up, or trust client-editable roles.
- Keep public browsing and existing local saves available. Separate device-only bookmarks from future authenticated synchronization, preserving data during adapter changes.
- Bootstrap Owner only through a trusted server-side operation for an explicitly verified provider UID. Restrictive rules and server-verified privileged endpoints must exist before exposing live privileged actions.
- Use actual metrics or explicit unavailable states. Browser collection, provider reporting access and internal app usage are distinct capabilities; document their evidence separately.

## Launch and monetization gates

- Confirm the target deployment, environment, build permissions and domain ownership before publishing or changing DNS. Preserve redirects and existing URLs, and disclose any unverified runtime behavior.
- Stripe readiness means a reviewed product/price decision, server-only secrets, verified webhook signature and idempotency boundaries, entitlement rules, and applicable policies. It does not mean live payments are enabled. Do not invent a store when only payments readiness is requested.
- AdSense readiness means substantial original public content, usable navigation, contact/privacy/terms disclosures, ownership and policy review, and appropriate consent handling for the intended audience. Do not promise approval or submit an application without authorization.

## Maintenance handoff

Keep a short project checklist of known gaps, deployment commit, verification performed, cost constraints and next authorized action. If recurring checks are requested, specify the source, cadence, allowed read or write actions, notification destination, and stopping condition. Store the reusable procedure here and project-specific schedule details outside this skill. Documentation alone is not an enabled automation.
