1. Keep canonical routes, redirects, labels, icons, and explicit allowed roles/capabilities in a shared route registry. Prefer top-level admin pages when available, such as /users, /features, /plans, /analytics, /observability and /feedback. Flatten admin submenu URLs independently of the sidebar hierarchy. Inspect existing static/dynamic pages, aliases, API and asset namespaces before choosing a path; use an admin namespace for actual collisions. A public /notifications or /domains page, for example, keeps that URL while its manager can remain under /admin. Preserve existing bookmarks through framework replace-style redirects when changing canonical URLs. Thin routes render components or redirects; keep account/page logic outside router files.

2. Use shared role values and capability helpers for permissions. Profile and own private tools require an active authenticated account. Dashboard, Feedback, Analytics, Observability and every ADMIN route require an active trusted Owner by default; Admin/Developer role names do not grant access. All non-Owners see Profile only as top-level account navigation, with supported Connections/My Submissions inside Profile. A user-selected policy may explicitly grant another role narrower capabilities; map that exception consistently through navigation, direct routes, services, rules and server endpoints. Preserve narrower record/participant boundaries from [Admin guidance](../admin/admin.md). Public browsing, eligible profiles/feeds, authentication, styles, and policy pages remain public unless a private app is requested. Gate identity-required actions.

3. Keep conventional sign-in aliases such as log, sign, login, log-in, and sign-in pointing to signin. Point new, sign-up, register, and subscribe to signup. Use replace-style redirects where supported so the back action does not loop through aliases.

4. Preserve useful feature aliases where applicable: config and general to settings; chat, chats, and message to messages; alerts and notification to notifications; edit, account, and preferences to profile; theme, design, components, and typography to styles. Do not create unrelated feature pages just to populate this registry.

5. Point info, aboutus, company, aboutme, about-us, and about-me to about. Point contactme, contactus, getintouch, get-in-touch, contact-me, and contact-us to contact. Include terms-of-service to terms and privacy-policy to privacy. Deduplicate aliases and avoid conflicts with existing canonical routes.

6. Resolve authentication state before checking protected access. Show "Sign in to view this" with sign-in and sign-up actions on private account pages for signed-out visitors, and an appropriate access message for users below the required role. Enforce the same access rule for direct URLs and navigation; a top-level admin URL retains its capability checks. Public social routes still use service-enforced record audiences; a public route never grants access to private data. Preserve minimum-role metadata where needed without using enum order to grant unrelated operational capabilities.

7. Navigation, profile menus, and mobile menus should use consistent icons from the installed icon library. Keep icon identifiers or mappings in route metadata; do not install multiple libraries simply to duplicate an example. Give interactive elements descriptive IDs and classes or native equivalents.

8. About, Terms, Contact, and Privacy Policy links must navigate to pages rather than section anchors before publishing. Resolve canonical and registered legacy internal return destinations after sign-in; reject external or unregistered targets. Derive links, active parents, full-width header/account-shell/loading classification and return destinations from the registry's account/admin metadata, including Profile, root admin pages and legacy aliases. Do not assume a private page starts with /admin. Keep the server's existing private API URLs separate from page-route changes.

9. Use the framework's supported router instead of constructing a second routing system. Refer to [structure guidance](../structure/structure.md) for module boundaries, [authentication guidance](../authentication/authentication.md) for sessions and roles, and [social guidance](../social/social.md) for public profiles, feeds, and private conversations.

10. A requested [full App System](../app-system/SKILL.md) adds public Pricing, Blog/article/category routes, private participant chat, Owner Features, and authorized catalog/content management to the shared registry. Reuse working routes and aliases; choose available root admin URLs and retain namespaced fallbacks for public/private collisions. Profile-owned tools can remain under /profile. The registry exposes only supported sections and applies the same capability/participant boundary to direct URLs as navigation. Public article routes cannot reveal drafts; pricing routes do not create entitlements. See [the account layout](../admin/layout.md) for Dashboard/Feedback parent links, expansion controls, child order and persistence.

11. The route registry also supplies analytics page identities: canonical/alias paths, readable labels and matching navigation icons. Resolve longest segment-boundary matches safely, retain raw paths/patterns and use a neutral document fallback. Navigation visibility and descriptive icons do not grant data access; direct routes and all provider/private record services enforce the same explicit capability as [Admin](../admin/admin.md).
