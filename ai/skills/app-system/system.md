# Complete Reusable App System

Use this blueprint when the user asks to implement the full common core. Extend an existing app through its own architecture; a new app follows AGENTS.md's framework defaults. Preserve product-specific feature models, routes, colors, and fonts while applying the shared account shell and working interactions. The common core is reusable; the app's business purpose and content remain its own.

## One Adoption Prompt

After copying ai/ and AGENTS.md into the destination repository, use:

> Implement the full App System from ai/skills/app-system/SKILL.md and ai/adoption.md in this project, completing every common-core module through real services, account-scoped realtime persistence, rules/indexes, and protected analytics. Include the shared Profile/Admin shell and menus, private Connections, Owner Features controls, and available top-level admin URLs with collision exceptions and old aliases. Preserve the project's framework, theme, features, data, and narrower permissions. Use its authorized configuration, follow AGENTS.md, and report source completion, actual connectivity, external setup, and validation separately.

This requests the whole core below. For account/profile/admin setup alone, use [the connected account prompt](../../adoption.md#connected-account-system-prompt); other focused tasks apply only their relevant module. Existing working integrations count toward completion; do not replace them merely to match a suggested folder or schema.

## Adoption And Integration

Inspect the current app before editing: determine routing/framework, shell/theme, shared persistence/API boundaries, session-to-User mapping, roles, actual configured cloud scope, static/dynamic content, and existing data. Map reusable feature contracts to those boundaries. Keep the mapping and any compatible migration plan in project documentation such as docs/APP_SYSTEM.md, outside ai/. Do not overwrite schemas, IDs, role values, static articles, or account preferences without a compatible path.

Follow the shared data flow: typed records and helpers feed services, services normalize storage and enforce operations, context/hooks expose scoped state, components render it, and routes remain thin. Add focused shared modules for chats, plans, and blog only where required. Share behavior across web/native while using their supported rendering and styles. Reuse the same Firebase instance, account state, capability helpers, route registry, and storage adapter; avoid duplicate caches or authentication systems.

Keep public home, legal pages, published articles, active pricing, and eligible notifications/Contact available without sign-in when their effective flags and audience permit it. Require identity for private Profile and chat actions. Use explicit capabilities for administration: Owner manages trusted roles/configuration, Admin has granted operations, Developer has granted technical reports, Subscriber has own-account features. Preserve stricter existing contact/message policies. Pricing publication cannot assign a User plan, alter roles, or establish payment entitlements; a minimum-plan feature selector reads the existing hierarchy rather than granting a plan.

Write restrictive rules alongside each new collection and matching bounded queries/indexes. Public projections contain only their intended display fields; private messages, contact details, account credentials, role records, drafts, and read state do not leak through public records or counters. Use app-owned stable IDs/numbers and atomic allocation as described in Admin. Include permitted create/update fields and immutable identity/ownership checks, including when clients call services directly.

Compose one shared account shell for Profile, Admin, Dashboard, chat management, plans, and authoring. Use the layout reference's measured header offset, full-width content, flush-left sidebar, persistent collapse/submenus, profile controls, matching loading states, responsive tables, and reporting geometry; retain the destination theme and fonts. ACCOUNT contains supported own-account links. ADMIN contains Dashboard with authorized Users, Events, Plans, Notifications, Reports, Analytics, Health, and Owner-only Features last; Feedback follows Dashboard with its supported Forms, Reviews, Chats, and Messages children. Keep deliberate destination restrictions and unsupported module states visible in the implementation map; menu grouping does not grant access or require nested URLs.

Keep the Dashboard overview ordered as Traffic, Health, adapted business activity/distribution charts, then concise count links sourced from the destination's real records. Retain relevant report KPIs, chart controls, source/coverage/freshness, and genuine warnings or errors. Do not append a redundant realtime-database/registered/loaded banner, recent-record panels, or intake tables beneath the overview. Operational record management and form review belong on their relevant permitted pages; match this overview structure in its loading shapes.

Prefer an available top-level URL for each admin page, such as /features or /users. Keep the existing admin namespace where the root path belongs to a public feature or is reserved, and preserve previous URLs with replace-style aliases. Use route capability metadata to recognize the account shell, select loading/navigation state, resolve safe sign-in returns and aliases, and supply analytics page labels/icons; do not infer administration solely from an /admin prefix. API endpoint namespaces and public static-asset paths remain independent of page URLs. Store the destination's actual mapping outside ai/.

Implement Owner feature configuration through [the feature contract](../admin/references/features.md), using one effective global/role/minimum-plan decision across headers, profile controls, menus, direct feature pages, listeners, and permitted persistence boundaries. A disabled theme control forces dark appearance while retaining the saved preference. Marquee changes remeasure the shared header. Notifications/Contact availability controls public access without removing authorized management/review. Preserve unknown or failed configuration as an explicit state; hidden controls alone are not authorization. Public frontend sections retain the app's design while sharing its theme/icons. Legal content describes actual behavior and feature availability, not imaginary payment, email, or sharing features.

## Detailed Integration Contracts

Follow [adoption](../../adoption.md) and the focused [Firestore/accounts/rules map](../admin/references/firestore.md), [private connections map](../admin/references/connections.md), [notifications/forms/actions map](../admin/references/workflows.md), [feature configuration map](../admin/references/features.md), and [analytics/runtime/icon map](../admin/references/analytics.md). Preserve working code and documented stricter policies. Source gaps in an existing app remain explicit: device/visit notification read preferences are not account-synced read state, transactionally allocated form IDs do not deduplicate retries, and a web-only provider adapter does not implement native reporting. Coming Soon Reviews, AI Chats, and Messages routes are navigation shells, not evidence of persisted reviews, an AI provider, or participant-private chat. Focused adoption may retain disclosed placeholders; the full starter must complete its required real chat and publication workflows without implying that unrelated business modules are connected.

Build real frontend-to-service-to-persistence/rules actions for every requested module. The connected source target includes stable identity/counters, current authorization, listener lifecycle, failed-save draft recovery, recipient/delivery separation, real report ranges/units/nulls/cache/coverage and full local identity assets. Copying these instructions alone does not perform cloud configuration or deployment.
