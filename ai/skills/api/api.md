1. Give each app an internal API or an equivalent shared asynchronous service. Use the existing framework: HTTP handlers where a server exists, or a typed local service for Expo and client-only apps. Keep the interface stable so a backend can replace local persistence later.

2. Provide a base /api directory describing available operations, a title, a concise connection message, storage mode, timestamp, and success status. Health and status operations may return the same response. Report real uptime, CPU, and memory only when the runtime exposes them; do not fabricate server statistics in a browser or mobile app.

3. Include /api/health, /api/status, /api/users, /api/notifications, /api/visits, and applicable model CRUD operations or their service equivalents. Use typed records from shared/models. Empty collections are valid; keep sample data optional and separate from persisted user data.

4. In a server development environment, the base directory may list registered API routes. Derive paths from the actual router or an explicit operation registry, normalize them, and avoid exposing filesystem paths. Do not copy Next.js filesystem traversal into Expo, Angular, or another incompatible runtime.

5. Keep persistence mode in shared configuration and route operations through the shared adapter. Preserve a single existing useLocalStorage switch for an explicit local demo; connected apps use their configured backend by default. Honor an explicitly selected session-only mode and describe it accurately. Missing configuration or provider failure must not become successful local authentication or a silent local data fallback.

6. Keep reusable model and authentication operations separate from feature-specific operations. Use focused service facades such as api/auth.ts, api/notifications.ts, and api/social.ts where those concerns are requested. A local service can expose getRoutes(), getHealth(), getUsers(), getNotifications(), and getVisits(), alongside the requested feature's CRUD methods. Public directory entries describe capabilities; they do not imply an HTTP server exists.

7. Model-backed cards, rows, and other repeated records should have their own components. Load them through the internal API or equivalent service, including data sourced from local storage, JSON, variables, or sample modules. Show skeletons while the operation is pending, then render the records or an honest empty or error state.

8. Keep request, response, loading, and error types consistent across local and backend implementations. Normalize data at the service boundary, preserve stable app-owned IDs, and propagate failures instead of returning success with empty data.

9. Keep backend and external-provider secrets out of client bundles, public records, and logs. User-entered local demo connection credentials belong only to private account-scoped settings, separate from public User records; a real backend owns production secrets. Social reads return explicit public or participant projections and enforce audiences before returning records. Authenticated mutations derive the actor from the session. Client-side local demo role gates do not replace backend authorization when real endpoints are connected.

10. Read [database guidance](../database/database.md) for persistence/models, [authentication guidance](../authentication/authentication.md) for sessions, [social guidance](../social/social.md) for profile audiences, [route guidance](../routes/routes.md) for page access, and [Admin guidance](../admin/admin.md) for privileged endpoints and dashboards. Keep implementation practical and scoped to requested operations.

11. Analytics/observability facades return typed reports with actual source, range, freshness, and unavailable/error states. Privileged endpoints verify the configured provider's session/token and current role/status (Firebase tokens in a Firebase app), keep provider tokens server-side, and fix authorized project scope. Bound filters, timeouts, caches, and request concurrency. Use verified provider contracts or trusted aggregate ingestion; never fabricate statistics.

12. Contact intake uses the typed persistence service and confirms success only after the submission commits. Allow validated guest creation for a public contact form, including honeypot enforcement, while keeping reads and review mutations private. Save independently of optional email delivery; return truthful saved/delivery states and preserve failed-save drafts. Follow [Admin contact guidance](../admin/admin.md#contact-intake-and-private-request-review) for atomic IDs, authorized realtime review, New/Read/Archived status actions, and paged search/filter disclosure; preserve existing stricter review permissions.

13. Use [App System](../app-system/SKILL.md) for a requested full starter, and its focused [chat](../app-system/references/chats.md), [plans](../app-system/references/plans.md), and [blog](../app-system/references/blog.md) contracts for those services. Expose typed subscription/page/mutation operations with permission and persisted-result semantics; a static page is not a completed API. Participant chat reads are private, published plan/article reads are public safe projections, and authoring/publication remains capability-controlled. Provider resource feeds are optional and cannot fabricate fallback content or expose server credentials.

14. Use [the workflow contract](../admin/references/workflows.md) for typed committed mutation results, private read-state hydration, configurable form validators/status/recipient maps and stable intake/delivery idempotency. Use [the analytics contract](../admin/references/analytics.md) for current authorization before caches, strict typed filters/ranges, private responses and honest source/unit/coverage errors. Components consume one facade; no route-local duplicate persistence or caller-supplied authority.

15. Connected account setup includes [feature settings](../admin/references/features.md) and [private provider connections](../admin/references/connections.md) through typed service boundaries. Verify the current active account/capability for privileged saves, syncs and environment imports; bind server credentials to an authorized account/resource instead of accepting caller-supplied authority. Return safe connection metadata and confirmed save/verification/sync states. Apply the relevant feature audience in the service and rules/server operation, including public notifications and Contact intake; hiding a button is insufficient enforcement. Page URLs and private API paths are separate registries.

16. Requested payment/subscription operations and reports follow [Payments](../payments/SKILL.md). Authenticate Checkout/Portal actions, bind the verified actor to private server-owned billing records, and validate approved offers rather than trusting client amounts/customer IDs. A signed webhook verifies raw bytes and provider/app scope before retry-safe persistence; its signature is its authority, not a browser session. Owner reports authorize before cache and expose typed aggregate projections only. Follow [Deployment](../deployment/SKILL.md) when publishing private APIs; a static export or eager server import is not proof the hosted handler starts and enforces authentication.
