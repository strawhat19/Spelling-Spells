1. Use Firebase Authentication with Google and email sign-in/sign-up for new full applications and requested connected account/admin systems unless another provider is chosen. Preserve the existing service interface and use the platform-supported provider flow. Local authentication is an explicitly chosen demo; missing Firebase configuration shows a connection-needed state rather than pretending to authenticate. Read [Admin guidance](../admin/admin.md) for provider setup and server authorization.

2. Keep authentication operations in a shared service and expose current-user state through React Context, or the existing framework's equivalent. Forms, menus, and protected pages should use that shared state instead of reading storage themselves. Hydrate the session before deciding whether a protected route is accessible. Public browsing remains available unless a private app is requested; show sign-in and sign-up when an action requires identity.

3. Use the shared User model, Roles enum, ID helpers, and storage adapter. New sign-ups default to Subscriber, profile visibility defaults to private, and optional public sharing starts disabled. Do not silently assign Owner to the first sign-up. Whitelist editable profile fields so ordinary updates cannot change roles, record identity, or account ownership. Preserve supported provider profile data when adapting a real backend.

4. Let Firebase manage connected credentials, persistence, password reset, verification, and sign-out; do not implement a second password store. Local authentication remains a device demo, with credentials separate from public users and no plaintext passwords. Clear account scopes, listeners, and cached state on sign-out, account changes, deactivation, or failed account loading. Backend authorization checks the current role/status independently of navigation controls.

5. After sign-in, always show an avatar in the app shell: use the provider photo when present, otherwise a colored circle with the first letter of the user's name capitalized. Match the app's navigation and mobile menu styling.

6. Open the profile menu by click or tap, with hover support where useful. Include consistent icons, a Profile link, and Sign Out at the bottom. Allow keyboard use and dismiss the menu when navigation or sign-out completes.

7. Give the current user's account Profile its own authenticated page with a Profile side menu or the mobile equivalent. If unauthenticated, show "Sign in to view this" with sign-in and sign-up actions. Public social profiles use separate safe projections and audience rules. Account connection settings belong to the profile management flow but keep credentials in separate private account-scoped storage. Keep access rules in shared route metadata.

8. Protect Dashboard and admin sections through shared explicit capabilities. Owner and Admin receive operational dashboard access; Developer receives technical reporting access without automatic user/role management; Subscriber retains own-account access. Preserve existing role values and narrower app policies. Show useful application statistics and animated charts from actual data, with honest empty/error states. Never invent activity or seed accounts to populate a dashboard.

9. Expose loading, error, and submission state through the shared service or context. Use skeletons while account data loads and concise Title Case toasts for outcomes. Keep the current user and persisted user record consistent after a profile change.

10. Apply [database guidance](../database/database.md) when persisting users or sessions, [API guidance](../api/api.md) for service operations, [social guidance](../social/social.md) for public profiles, privacy, and authenticated social actions, and [route guidance](../routes/routes.md) for roles and redirects. Follow the chosen framework and preserve existing user data during adoption.

11. In a requested [full App System](../app-system/SKILL.md), define chat participation and catalog/article authoring capabilities explicitly. A dashboard role does not grant every private chat or existing Owner-only contact inbox. Ordinary profile edits cannot change plan/entitlement fields; [pricing publication](../app-system/references/plans.md) is separate from trusted account access. Public contact intake, published blog, active pricing, and public notifications retain their intended guest access.

12. Follow [the detailed account contract](../admin/references/firestore.md#sdk-providers-and-private-configuration) for UID mapping, concurrent hydration deduplication, authoritative role/status, token/server authorization and lifecycle cleanup. Map existing role case/scalar/array values deliberately; unknown roles fail closed. Keep Subscriber creation, trusted ownership/access auditing and last-Owner policies distinct from ordinary profile edits.

13. Evaluate [feature audiences](../admin/references/features.md) from the authoritative current role, active status and trusted account plan, using Guest/Free for signed-out visitors. A missing confirmed settings read is pending/unavailable rather than implicit permission. The feature provider depends on account state and the effective theme depends on the theme feature; keep their provider order consistent. Preserve saved theme preferences while disabled theme controls force dark mode, and prevent initial light-mode flashes. A pricing selection, profile edit or caller-supplied role/plan cannot grant entitlement or feature-management access.
