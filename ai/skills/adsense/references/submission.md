# AdSense Submission And Review

Use for website submission preparation and authorized AdSense Sites actions. Preserve the destination framework, hosting, public URL prefix and existing monetization. Website AdSense does not configure native-app advertising; native monetization needs a separate supported integration and distribution-policy decision.

## Scope And Account Authority

Use the existing authorized publisher account and intended website. Do not create another account, enable advertising, publish consent messages or accept commercial/legal choices merely because preparation instructions mention them. Complete actions already authorized; request input only for missing account-holder details, legal decisions or additional scope. Never invent payee identity, country, address, tax information, consent or acceptance of terms.

Keep real domains, publisher IDs, deployment IDs, account details and dated evidence in destination configuration/docs outside ai/. A publisher identifier is public; credentials and account-holder information are not.

## Public Content And Navigation

Prepare useful original public content that explains the site's purpose and provides substantive value. Distinguish authored articles from external resource feeds; links, copied excerpts and embedded videos do not establish first-party authorship. Do not manufacture filler, publication history, testimonials, readership or a guaranteed qualifying article count.

Provide readable About, Contact, Terms and Privacy pages with persistent internal navigation. Show complete policy text, not only the first fragment behind pagination. Contact details or forms must reflect actual supported communication; do not claim delivery from an unconnected form. Disclose actual data/payment/advertising behavior and conditional future behavior accurately. Preserve public browsing without weakening authorization for private account data.

## Crawling, Metadata And Errors

Prefer substantive content and stable titles, descriptions, canonical URLs and verification metadata in the initial HTML. A JSX head component or browser inspector alone does not prove what a raw HTTP response contains. When checks are authorized, inspect raw HTML and rendered output separately. Google's [JavaScript SEO guidance](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics) explains rendering, crawlable links and meaningful status codes.

Use real links and known public routes. Adapt canonicals and sitemap entries to the actual origin/prefix; exclude private workflows, duplicates and nonexistent articles. Allow required rendering assets and intended public crawler access. Unknown paths should return genuine 404 responses where supported; preserve explicit noindex on error fallbacks rather than serving a successful Home page everywhere. Robots/noindex controls do not authorize users or replace authentication. Do not assume Search indexing or its rendering behavior establishes AdSense crawler access or approval.

## Real Publisher Configuration

Obtain the actual publisher identifier from the selected account, validate its supported format and configure the intended production environment. Never ship an invented or all-zero identifier. Missing/invalid configuration emits no verification tag or fabricated seller record; a generated provider-only ads.txt endpoint should return 404 until configured. Preserve other legitimate existing seller entries.

Serve the matching ads.txt authorization at the domain root, even when the app uses a public path prefix. When authorized, confirm its actual response status, plain-text content and matching account identifier; an HTML fallback is not ads.txt. Redeploy when configuration is captured at build time.

Google's [site connection instructions](https://support.google.com/adsense/answer/7584263?hl=en) distinguish code, ads.txt and meta-tag verification. Metadata/ads.txt can connect a site without adding an advertising loader. Record loader installation and Auto ads configuration separately; neither verification nor an approval message proves placements, consent readiness or ad delivery.

## Review And Consent Setup

Add the intended site, use the chosen supported verification method, confirm verification and request review only within existing authorization. Record the actual site-detail status. Pending review is not approval; successful HTTP checks do not guarantee eligibility, review timing, traffic, advertising fill or earnings. Do not repeatedly resubmit solely because a status has not changed.

Choose Google's CMP or a certified third-party option supported for the site's current requirements. In Privacy & messaging, confirm selected sites, languages, privacy-policy URLs, appropriate geographic targeting and publication status. Review refusal and management choices against current requirements and the owner's authorized decisions. A saved draft is not published, and a local cookie popup is not evidence of configured Google consent handling. Google's [European message workflow](https://support.google.com/adsense/answer/10960768?hl=en-GB) distinguishes these settings and publishing from saving a draft.

Address applicable [US state privacy messages and opt-out choices](https://support.google.com/adsense/answer/10961479?hl=en) as well; do not copy a permanently fixed list of jurisdictions. Message configuration does not prove that a visitor consented. Keep privacy pages reachable and respect actual refusal/withdrawal through the separately implemented advertising lifecycle.

## Evidence And Handoff

Separate source preparation, configured publisher resources, deployed revision, live HTTP/HTML readback, consent-message publication, submitted review and actual ad serving. Preserve screenshots as dated dashboard evidence, not as crawler or traffic data. A stale crawler/dashboard status can lag a release; compare timestamps and current responses rather than dismissing real 404s, wrong identifiers or missing metadata as lag. Report unresolved setup precisely and wait for Google's actual decision.
