# Private Account Connections And Realtime Sync

Read this for Profile connection settings, provider verification, or connected account data imports. Reuse the destination's shared authentication, storage/API facade, capability helpers, and measured account shell. Apply [Firestore](firestore.md) for identities, allocation, queries/rules, [workflows](workflows.md) for committed actions and account resets, and [layout](../layout.md) for fields, status cells, badges, and loading states. A focused connection setup does not add providers or business modules unrelated to the app.

## Private Metadata And Credentials

Separate an account's connection metadata, production credentials, and imported business records. A connection has a stable app-owned ID/number, owning account, provider/type, permitted external account or project reference, configuration revision, and safe verification/sync metadata. Support multiple connections to one provider when the destination does. Keep external service IDs in named fields; they do not replace app-owned primary IDs.

Own connection metadata and status belong in private account-scoped persistence, separate from public User/profile records. Subscribe to that metadata through actual Firestore realtime listeners in a connected Firebase implementation. Production credentials belong behind the server boundary in private protected storage or the configured secret system. Ordinary clients receive safe configured/masked indicators and permitted metadata, not stored tokens, passwords, secret environment values, or refresh credentials. Sensitive fields stay out of public records, frontend bundles, logs, error bodies, analytics events, exports, and shared caches. A hidden input or masked rendering does not change who can read its underlying record.

Credential entry can pass from a labeled masked form to the authenticated server save endpoint. Validate provider-specific allowed keys, required combinations, types, sizes, and supported account/project scope before storage. Return a typed committed metadata result and discard submitted secret text from ordinary client state after a successful save. Preserve failed drafts only within the originating account's permitted editing context; never persist production secrets to browser storage as an automatic fallback. Use the platform's suitable private credential storage and document its actual access policy outside ai/.

Some references store raw credential text in client-readable private records, relay caller-supplied credentials, or import deployment environment values after checking only that a user is active. Those behaviors may provide existing account-scoped persistence or a local demonstration; they do not establish the server-owned production-secret boundary. Preserve existing data and describe any required compatible migration, account binding, and endpoint changes honestly. Do not silently delete saved connections, publish credentials, or claim that copying the pack completes that migration.

## Actor And Operation Boundaries

Load, save, verify, sync, and clear operations derive the actor from the authenticated session and current app-owned identity. Recheck active status, explicit capabilities, permitted plan/provider access, and resource ownership at the service/server boundary and in matching database rules. A caller-supplied user ID is an expectation to compare, not authority. Scope credentials, provider caches, imported records, counters, and subscriptions to that same account and connection. Administrative status alone does not grant another user's private credentials.

Expose typed operations through one facade: own metadata load/subscription, allowed configuration save, provider verification/sync, and scoped disconnect/clear. Save immutable identity/ownership separately from allowlisted editable fields; verification and provider-result fields come from trusted operations. Check concurrency through current revisions, transactions, or equivalent conflict handling so a late save cannot overwrite another device's changes. Enforce real account/provider limits at the authoritative mutation boundary as well as in the UI.

The provider server verifies the Firebase token or supported session, resolves its current account, and authorizes the selected saved connection before reading secrets or returning cached data. A normal recurring sync sends a connection reference and permitted options; the server selects that account's saved credentials and fixed provider scope. Validate any credential-entry request as a separate authorized operation. Use allowlisted provider adapters and destinations, bounded request/response sizes, timeouts, pagination, concurrency, and relevant server rate limits. Same-origin request checks alone do not establish account ownership. Provider errors return useful redacted messages rather than raw secret-bearing responses.

## Environment And File Imports

Deployment credentials require an explicit account/project/team binding and allowed-operation policy. Server environment import is not a way for every authenticated user to download deployment secrets. Default to creating or updating an authorized private server binding and returning safe imported/skipped/error metadata. If an existing application deliberately permits credential export, preserve and document that narrower explicit capability; do not infer it from ordinary sign-in or a profile role.

Use a provider-specific allowlist for imported environment names and bounded literal values. Read a user's selected file as data, not executable shell text. Treat an imported draft, a saved configuration, a successful provider verification, and a committed business-data sync as distinct outcomes. Do not label an unsupported OAuth/reseller/hosting mode Connected merely because its fields were saved. Keep actual providers, environment names, allowed scope, account bindings, schema paths, and migration history in the destination's code/configuration/docs outside ai/. Portable examples use placeholders rather than another project's IDs or secrets.

## Verified Availability And UI State

The shared availability source combines the current account's live metadata with verification tied to the same connection revision and supported capability. Nonempty credential text means Configured, not Verified or eligible for every provider operation. A changed credential or scope invalidates the old verification until the current configuration is checked. A supported provider may verify successfully with zero imported records; zero records alone does not mean failure.

Expose Loading, Not Configured, Saved/Unverified, Checking, Connected, Unsupported Operation, Connection Needed, Access Denied, and Failed distinctly. Keep refresh available to recover from read failures. A verified-count badge uses current eligible connection states, preserves Loading/error presentation, and does not display an unavailable count as a confirmed zero. Multiple accounts per provider retain their own status; any aggregate has defined coverage. Separately configured public server capabilities can enable a public tool without implying that the visitor owns a private connection.

Use the same availability state in Profile, sidebar badges, menus, business tables, and sync actions. Inputs and actions retain accessible labels/icons and stable record IDs. Show the last confirmed status, last successful verification/sync, current attempt/error, and source/cache freshness without conflating them. A save succeeds only after persistence confirms it; report a subsequent verification or import failure separately and keep the saved configuration accurately described.

## Normalize And Commit Imported Records

Provider adapters return typed normalized records, warnings, limits/coverage, and source/fetch metadata. Validate identifiers, names, dates, units/currencies, booleans, nullable fields, and supported response shapes before app persistence. Keep unavailable values unknown rather than turning them into zero, false, invented ownership, or guessed registrar identity. A hosting provider and the actual registrar can differ. Only import the account's permitted owned or explicitly supported linked resources; discovery results do not automatically prove ownership.

Upsert into the destination's existing domain/app/business models using a documented account-scoped deduplication key, such as a normalized owned domain or an external record reference. Preserve existing app-owned ID, number, created time, manual annotations, and user-managed fields. Allocate new stable IDs/numbers atomically with the relevant account/collection counter, store provider IDs in named external fields, and record safe provider/connection provenance. Repeating a sync should update the same records rather than allocate duplicates or rekey them. Match the actual rules and transaction limits; disclose partial chunk commits and make retries safe.

Persist only allowed provider-managed fields and validated safe metadata. Distinguish created, updated, unchanged/skipped, and failed counts after committed writes. Avoid deleting records merely because a provider failed, returned a truncated page, omitted an unavailable field, or produced an empty partial result. Destructive reconciliation needs an explicit ownership/completeness policy. Keep last successful data available with a stale/error label when an attempt fails; a provider fetch alone is not proof that its results saved to Firestore.

Business tables subscribe to the same account-scoped persisted records, using bounded queries/cursors and supported indexes. Search/filter/export scope reflects the loaded page/window unless a real broader service exists. Do not maintain a second disconnected local portfolio, announce global totals from a partial provider list, or claim realtime provider collection merely because saved Firestore records stream in realtime. Cache keys include account, connection, configuration revision, and query/scope; expose actual cache freshness and invalidation.

## Lifecycle And Scoped Clearing

Tag asynchronous work with account/login revision, connection/configuration revision, and operation identity. Abort provider requests, dispose listeners, invalidate caches, and clear another account's visible data/secret drafts on account switch, logout, deactivation, connection change, or unmount. Ignore late results before displaying or committing them; recheck authoritative ownership immediately before writes. A stale request must not import into the next account or recreate records after that account cleared its data.

Disconnect or clear only the selected own connection, credentials, verification/cache state, and explicitly requested imported records. Define whether disconnect retains imported business records; do not assume it deletes them. Coordinate account resets with active sync/writes, preserve monotonic counters and unrelated manual data, and prevent automatic sync from repopulating a deliberately cleared account until its policy permits it. Provider-side revocation is a separate supported action. Keep malformed snapshots and failed deletes explicit instead of replacing them with a successful empty state.

## Connected Target And Handoff

A completed connection module has working metadata/credential operations, current actor verification, actual provider validation, typed normalized upserts, real Firestore subscriptions, scoped reset/lifecycle behavior, matching restrictive rules/indexes, and truthful saved/verified/synced states. Existing private client-readable storage, optimistic snapshot revisions, and cached verification can be reused where appropriate, but are not proof that production secrets, provider authorization, or current availability satisfy this contract.

Report Source: Complete/Incomplete, Connection: Connected/Setup Needed/Unavailable, and Validation: User Review Pending/Checks Performed with actual evidence. Identify the destination's required Firebase configuration, deployed rules/indexes, hosted server, secret policy/binding, provider account/API entitlement, and missing supported operation separately. A public SDK configuration, pasted token, or empty listener does not confirm a working sync. Follow AGENTS.md for checks and external actions; this guide does not authorize test/build/UI commands, cloud creation, secret import, deployment, or provider-side changes outside the user's scope.
